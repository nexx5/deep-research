# 技术调研

## 定位

目标是理解某项技术、工具、方案或系统的原理、能力边界、工程可行性、风险和适用场景。技术调研不能停留在概念摘要，必须追到架构、接口、实现、性能、约束和替代方案。

## source_strategy

优先采集：

1. 官方文档、架构说明、API 文档。
2. GitHub README、examples、docs、issues、releases。
3. 论文、技术报告、benchmark、评测文章。
4. 生产案例、迁移经验、故障复盘。
5. 竞品/替代方案文档。
6. 反方观点、已知缺陷、限制说明。

**学术引擎使用**：涉及论文/算法/模型溯源时，`sources` 必须含 `arxiv`、`openalex`。arXiv 覆盖 CS/AI 预印本，OpenAlex 覆盖全学科正式发表。Semantic Scholar 按需启用（引用网络追溯时有用，但限流严格）。学术论文的摘要直接作为 raw 内容；如需全文，下载 PDF 后用 opendataloader-pdf skill 提取。

## evidence_ranking

源码/官方文档/论文原文 > 可复现实验/benchmark > issue 与真实案例 > 深度技术文章 > 一般博客/转述。

## extraction_questions

- 这项技术解决什么核心问题？
- 它依赖哪些前提和运行环境？
- 核心架构组件是什么？
- 数据流、状态流、调用链如何运转？
- 对外接口、配置项、CLI、API 是什么？
- 性能数据来自什么测试条件？是否可复现？
- 与替代方案相比取舍是什么？
- 有哪些已知限制、失败场景和迁移成本？
- 哪些结论来自官方声称，哪些来自独立验证？

## synthesis_dimensions

架构模式、能力边界、工程复杂度、性能表现、可维护性、生态成熟度、风险、替代方案、落地路径。

## knowledge_schema_seed

technology / component / interface / configuration / workflow / benchmark / limitation / tradeoff / alternative / use_case / risk / evidence

## saturation_rules

至少满足：

1. 核心架构和运行流程闭合。
2. 关键接口、配置、部署或使用路径明确。
3. 性能/能力结论有来源和测试条件。
4. 至少覆盖一个替代方案或反面观点。
5. 已知限制和不适用场景明确。
6. 能回答“什么时候该用、什么时候不该用、怎么落地”。
