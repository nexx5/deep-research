# 源码调研

## 定位

源码调研是技术调研的深读形态。目标是形成无需反复重读代码也能用于问答、设计和对比的知识包，而不是简单列文件结构。

## source_strategy

优先顺序：

1. README、docs、architecture、design 文档。
2. package/module 入口文件。
3. CLI/API/RPC/服务入口。
4. 核心类型、状态机、主循环、调度器。
5. tests、examples、fixtures。
6. issues、PR、commit、release notes。

## evidence_ranking

源码实现 > 测试用例 > 官方文档 > issue/PR 讨论 > README 摘要 > 第三方解读。

## extraction_questions

- 系统入口在哪里？
- 一次请求/任务从入口到结束经过哪些模块？
- 核心状态对象是什么？如何变化？
- 错误、重试、取消、恢复如何处理？
- 对外扩展点在哪里？
- 配置如何进入运行时？
- 哪些文件是胶水，哪些是核心逻辑？
- 测试覆盖了哪些关键行为？
- 代码中有哪些隐含设计取舍？

## synthesis_dimensions

调用链、状态机、模块边界、扩展点、错误恢复、配置流、数据结构、并发/异步、测试证据、架构取舍。

## knowledge_schema_seed

package / module / file / function / class / type / state / event / command / tool / provider / config / test / flow / edge

## saturation_rules

至少满足：

1. 主入口链路闭合。
2. 核心状态机或数据流闭合。
3. 关键类型/函数/类有源码位置。
4. 错误路径和恢复路径有说明。
5. 测试或示例能支撑主要行为。
6. 知识包能支持后续“这个机制怎么运行”的问答。
