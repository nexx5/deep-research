# 调研策略层

本目录提供调研员的轻量策略层。它不改变主流程，只影响各阶段“怎么挖、怎么取证、怎么判断质量”。

## 三层模型

```yaml
research_type: 决定最终产物，可为主类型或最接近类型
research_subtype: 描述具体任务
strategy_tags: 决定来源处理和质量门
research_axis: 研究主轴/副轴，用于承载混合任务
type_notes: 分类说明，解释为什么这样归类
```

## 目录结构

```text
research-strategies/
├── types/       # 研究目标类型：最终产物是什么
├── scenarios/   # 强场景策略：具体任务怎么做
└── sources/     # 来源策略：不同来源如何采集、去噪、评价
```

## 分类决策原则

`research_type` 由最终产物和研究对象决定，不由表层场景词决定；`research_subtype` 描述具体落地任务或业务场景；`strategy_tags` 描述证据来源和取证方法。

分类不得成为单独确认闸门。除项目名缺失、用户目标互斥、或用户明确要求先讨论分类外，agent 不得只问“是否是技术类调研/某类调研”。分类判断必须写入 PLAN_REVIEW 草案，包含首选分类、置信度、反例风险和备选分类。

分类验收不看唯一答案，而看是否同时保留“研究主轴”和“落地场景”。混合任务允许 `research_type` 选择最接近类型，同时必须写 `research_axis` 和 `type_notes`。

若目标是“如何构建 agent/系统/方法论/工具链/工作流”，但落地场景是产品选型、决策支持、内容生产等，可接受 `research_type=技术调研` 或 `research_type=决策支持`；但必须在 `research_axis.primary` 标明 `agent构建/技术方法论/自学习机制`，在 `research_axis.secondary` 标明落地场景。若目标是“理解代码/运行机制/API/架构”，优先归为 `源码调研` 或 `技术调研`。

## 读取规则

调研员各阶段读取 `project.config.md` 后，按需加载：

1. `types/<research_type>.md`
2. `scenarios/<research_subtype>.md`
3. `sources/<strategy_tag>.md`

匹配不到具体策略时，必须回退到 `types/通用.md`，并在方案草案或质量记录中标注“策略缺口”。不得因为策略缺失而直接进入采集。

## 方案草案要求

PLAN_REVIEW 阶段的方案草案必须先输出“策略映射”作为第一个结构化产物；在策略映射表之前不得输出长篇背景、执行建议或报告式总结。策略映射章节必须使用固定表格，不得改成概述段落：

| 策略文件 | 字段模型 | 采集方向 | 取证问题 | 预期产出 | 策略缺口 |
|---|---|---|---|---|---|
| `types/<research_type>.md` | 从策略原文提取 | 本项目如何采 | 本项目要问什么 | 进入哪些文件/知识包 | 无/说明缺口 |
| `scenarios/<research_subtype>.md` | 从策略原文提取 | 本项目如何采 | 本项目要问什么 | 进入哪些文件/知识包 | 无/说明缺口 |
| `sources/<strategy_tag>.md` | 从策略原文提取 | 本项目如何采 | 本项目要问什么 | 进入哪些文件/知识包 | 无/说明缺口 |

表格完整性校验：

- 至少包含 1 行 `types/`、1 行 `scenarios/`、以及每个 `strategy_tags` 对应的 `sources/` 行。
- 每行 6 个字段都不得为空，不得写“待补充/略/同上”。
- 如果策略文件存在 `field_model`，必须原样展开或映射为本项目字段，不得压缩成“需求/痛点”等泛称。
- 如果行数不足、字段为空、未展开字段模型，必须自动补全；无法补全时标记“方案需修订”，不得请求用户确认执行。

策略映射必须同步落入：

1. `1-规划/1-任务规划.md`
2. `1-规划/task_queue.md`
3. `1-规划/4-知识包设计.md`
4. `project.config.md#strategy_mapping`
5. `project.config.md#knowledge_schema`

PLAN_REVIEW 合格条件：

- 不存在单独的“是否属于某类调研”确认闸门。
- 混合任务已写明 `research_axis` 和 `type_notes`，没有丢失研究主轴。
- 有“策略映射”章节，且它是方案草案的第一个结构化产物。
- 表格中列出实际读取的策略文件。
- 表格行数覆盖 `types/`、`scenarios/` 和每个 `sources/` 策略。
- 每行 6 个字段非空。
- 至少一个策略文件的字段模型被展开。
- 采集方向不是泛称，必须能转成 DISCOVER 任务。
- `project.config.md#strategy_mapping` 存在并可被机器读取。
- 知识包设计中能看到策略字段或其映射。

不满足任一条件时，必须标记“方案需修订”，不得请求用户确认执行。

如果用户需求中出现“需求、痛点、雷区、口碑、社区、评价、投诉、长期使用、后悔、功能是否有用”等词，agent 必须主动建议加入相关 `research_subtype` 或 `strategy_tags`，并读取对应策略文件。

## 当前内置策略

### types

技术类策略较成熟，作为发布版样板：

- 技术调研
- 源码调研

其他类型先提供最小骨架，后续扩展：

- 通用
- 决策支持
- 市场商业
- 文史人文
- 政策法规
- 知识创作
- 舆情用户研究

### scenarios

产品选型、需求发现与技术选型是当前重点场景：

- 产品选型
- 需求发现
- 技术选型

### sources

- 社区反馈
- 电商评价
- 售后投诉
- 官方参数
- 专业评测

这些字段只在相关场景启用，不作为所有研究类型的固定模板。

## 社区能力边界

当前版本先写入社区来源的分析原则。具体平台搜索、登录、抓取、正文提取能力由后续 skill 逐步补齐。

社区来源抓不到全文时，不得忽略；应记录为线索、死胡同或平台能力缺口。
