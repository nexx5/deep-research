# 技术选型

## 定位

技术选型是技术调研下的强场景策略。目标不是罗列工具功能，也不是按热度排名，而是建立“可执行的选型判断”：候选方案、适用场景、约束条件、能力边界、生态成熟度、成本、风险、替代路径和证据链。

## source_strategy

优先组合：

1. 官方文档：确认声明能力、接口、限制、许可证和版本边界。
2. GitHub / 源码仓库：验证维护活跃度、issue、release、代码结构和真实能力。
3. Benchmark / 评测文章：比较性能、稳定性和成本，但必须检查测试条件。
4. 社区反馈：识别踩坑、长期维护问题、部署失败和隐性成本。
5. 生产案例：判断方案是否真正被落地，而不是只停留在 demo。
6. 安全文档 / 合规条款：检查权限、数据边界、平台 ToS、隐私和法规风险。
7. 替代方案文档：用于建立 tradeoff，而不是只证明首选方案好。

## evidence_ranking

源码、官方文档、真实 issue、release 和生产案例优先；benchmark 只有在测试条件清楚时可采信；商业白皮书和博客只能作为线索；社区反馈用于发现风险，不能单条直接定性；过期教程和无人维护仓库必须降权。

## extraction_questions

- 这个技术选型要解决什么目标？目标是否可验证？
- 候选方案有哪些？分别属于官方 API、开源工具、商业服务、自研方案还是混合路径？
- 每个方案的核心能力是什么？哪些能力只是声明，哪些已被验证？
- 关键接口、协议、运行环境、部署方式是什么？
- 方案依赖什么外部条件？如账号权限、API 配额、浏览器环境、代理、企业认证、数据授权。
- 性能、稳定性、成功率、延迟、成本如何？测试条件是什么？
- 方案在哪些场景会失败？失败后如何降级？
- 安全、合规、平台 ToS、隐私风险是什么？是否可规避？
- 社区和维护状态如何？最近 release、issue 响应、核心维护者是否活跃？
- 文档质量和集成复杂度如何？弱团队能否落地？
- 迁移成本和锁定风险是什么？未来替换难不难？
- 现有方案之间的 tradeoff 是什么？为什么不选其他方案？
- 最终推荐路径是什么？MVP 用什么，生产版用什么，长期演进是什么？

## synthesis_dimensions

目标-约束匹配、候选方案矩阵、能力覆盖、接口与依赖、性能/稳定性、成本结构、安全合规、维护生态、集成复杂度、失败场景、降级策略、替代路径、推荐路线图。

## decision_matrix

技术选型至少形成以下矩阵：

| 维度 | 说明 |
|---|---|
| 能力覆盖 | 是否满足核心目标和关键场景 |
| 可获得性 | 是否能获取 API、账号、数据、权限、部署环境 |
| 稳定性 | 长期运行是否可靠，失败率和维护成本如何 |
| 成本 | 开发、运行、API、代理、云资源、人工维护成本 |
| 合规 | 是否违反平台 ToS、法律、隐私或安全边界 |
| 生态 | 社区、文档、issue、release、生产案例 |
| 集成 | 与现有系统/流程/agent 的接入复杂度 |
| 可迁移 | 替换方案或扩展平台的难度 |
| 失败降级 | 失败时能否切换官方 API、人工输入、缓存、第三方服务 |

## recommendation_pattern

推荐结论必须按层次输出：

1. MVP 首选：最低成本、最快验证、风险可控。
2. 生产首选：稳定性、合规、可维护性优先。
3. 补充方案：弥补首选方案的覆盖缺口。
4. 不推荐方案：说明失败场景和排除理由。
5. 待验证项：列出必须实测的 API、权限、成本、成功率或合规边界。

## saturation_rules

至少满足：

1. 核心候选方案已覆盖，不少于 3 类路径。
2. 每个候选方案都有能力边界、依赖条件、成本和风险说明。
3. 官方声明、源码/issue、社区反馈和生产案例至少覆盖其中 3 类证据。
4. benchmark 或成功率数据标明测试条件；无测试条件则只作为线索。
5. 合规边界已明确，尤其是 API 权限、平台 ToS、隐私和数据授权。
6. 推荐路线能区分 MVP、生产版、补充方案和不推荐方案。
7. 关键 P0/P1 待验证项已进入 task_queue 或 knowledge-pack 的 cannot_answer_yet。
8. 能回答“为什么选它、为什么不选它、失败怎么办、以后怎么替换”。
