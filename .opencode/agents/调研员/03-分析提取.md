# 分析提取

> 调研员子阶段：基于采集记录写单源分析 + 跨源对比 + 深度素材挖掘
> 本文件属于调研员，不独立调用。
> **职责边界**：A*/C* 是"客观证据台账"--如实记录这家说了什么、那家说了什么、它们在哪冲突。**不评判、不生产观点**（不判谁对谁错、不产出立场性结论）。观点生产归分析员。

## 深度挖掘前置（每轮必做）

分析前遍历本轮新增 raw 文件，从四个维度补充信息：

### 1. 图片分析（上下文判断 + 按需调用图片分析 agent）

遍历 raw 文件中的图片引用（`![]()` 或 `<img>`），结合上下文判断重要性：

| 判断为重要（触发分析）| 判断为不重要（跳过）|
|---|---|
| 架构图、流程图、拓扑图、数据可视化 | 头像、表情包、装饰背景、图标、banner |
| 截图（CLI 界面、UI 界面、代码截图） | 照片中与调研主题无关的元素 |
| 历史地图、古籍影印、手稿照片 | 广告图片、分隔符图片 |
| 产品/设备实物图（与主题直接相关） | SVG 图标、emoji |

判断为重要的图片：
1. 下载图片到 `01-采集记录/原始资料/assets/raw-S{id}-{seq}.{ext}`
2. 调用 `@图片分析` subagent（`task` 工具），传入图片路径 + 分析指令
3. 图片分析 agent 返回结构化描述 → 写入单源分析的"图片索引"节

### 2. PDF 内容提取

检查 raw 来源中是否有标记为"PDF待提取"的文件：
1. 在 `assets/` 中找到对应 PDF 文件
2. 调用 `pdfplumber` 提取文字 → 写入 raw 文件末尾追加内容
3. 调用 `pdfplumber` 提取表格 → 写入工程细节矩阵
4. 确认无误后去掉"PDF待提取"标记

### 3. GitHub 深度探索

检查 raw 来源中是否有 GitHub README（来源类型="GitHub README"）：
1. 根据调研上下文判断 repo 的探索深度
2. 若需要查看目录结构：`gh repo clone <owner>/<repo> -- --depth 1` 到临时目录，`ls -R` 关键路径
3. 若 scripts/ 或 src/ 目录包含可能的关键内容，`read` 关键文件 → 追加到 raw
4. 分析完毕后删临时目录（不污染项目仓库）

### 4. 富化工程细节矩阵

从上述三个步骤的产出中提取信息，补入采集记录的"工程细节矩阵"：
1. 图片分析产出 → 矩阵新增"附图"行
2. PDF 表格 → 补充到"关键数据"或对应维度行
3. GitHub 源码 → 补充到"实现细节/CLI/配置"行
4. 代码块完整性检查：原 raw 中代码块是否在矩阵中有对应行，无则追加

## 策略加载

分析前必须读取 `.opencode/research-strategies/types/`、`scenarios/`、`sources/` 中与 `research_type`、`research_subtype`、`strategy_tags` 对应的策略，优先使用其中的 `synthesis_dimensions` 组织单源分析和跨源对比。

## 触发与连续执行

- `task_queue.md` 中存在 pending EXTRACT 时，必须优先批量并发执行 EXTRACT，单批最多10个。
- EXTRACT 完成后，如果存在多个分析文件且缺少 `对比-C*.md` / `链-C*.md`，必须自动生成 SYNTHESIZE 任务并执行。
- 队列空但已有 `分析-A*.md` 且无跨源对比/链时，不得停止或询问用户，必须进入跨源对比。
- 不得因为“未分析采录数 < 5”而停止；采集暂歇、队列空、或已有单源分析但无跨源合成，均可触发 SYNTHESIZE。
- 禁止询问用户“先 SYNTHESIZE 还是继续采集”；由本阶段根据证据链自动决策。

## 单源分析

对每个采集记录写单源分析文件，写入 `02-分析提取/单源分析/分析-A{id}*.md`：

```
# 分析提取：{来源标题}

分析ID: A{3位}
来源ID: S{3位}
采集记录: 01-采集记录/采集记录-S{id}.md

## 核心价值
对本项目的价值点。具体：哪个设计/决策/思路可以参考。
1. ...
2. ...

## 差距分析
与本项目目标对比，存在哪些差距（不足/缺失/不适用）
1. ...
2. ...

## 设计含义
对本项目架构/设计的直接影响。具体建议：可以抄什么、怎么调整。

## 局限性
该来源自身的局限（非对本项目的），可能影响迁移。

## key_claims（结构化断言，知识管理员提取用）

> **格式权威：见 standards/extraction-format.md——唯一格式定义，本节示例与之保持一致；如不一致以 standards 为准。**禁止 bullet + `**CL{id}**` 前缀，claim_id 不在此预占（知识管理员 ingest 时分配）。
> 每条断言 = 主体 + 关系 + 客体 + 边界条件 + 置信度 + 来源。
> 断言是知识体系的原子单元，必须简洁精确，不是完整句子。
> boundary 是"在什么条件下成立"，不是结论本身。缺失时写"未明确"。
> 如果本分析的结论扩展/修正/否定了既有结论，在 supersedes 列填写被影响的断言ID。

| # | subject | predicate | object | boundary | confidence | sources | supersedes |
|---|---|---|---|---|---|---|---|
| 1 | {主体概念} | {关系/属性} | {客体概念/值} | {边界条件} | H/M/L | S{id} | CL_xxx 或空 |
| 2 | ... | ... | ... | ... | ... | ... | ... |

示例：
| 1 | RedFoxHub | 提供 | 微信公众号正文读取路径 | 使用第三方数据源+RedFoxHub数据来源合规 | M | S062 | |
| 2 | RedFoxHub | 提供 | 小红书搜索+详情API | 使用第三方数据源 | M | S062 | |

## extracted_claims_confirmation（知识管理员回写，调研员不填此段）

> 知识管理员 consolidation run 时填写，确认断言已入库。

| # | db_claim_id | status | extracted_date |
|---|---|---|---|
| 1 | CL_A062_1 | active | 2026-06-26 |
```

**key_claims 编写规范**：
- subject/predicate/object 必须是简洁的概念/关系，不是完整句子
- 一篇 A* 通常产出 2-8 条断言，不要过度提取
- boundary 必须写明适用条件，不能省略（写"未明确"也比不写好）
- 如果本分析推翻或扩展了既有结论，supersedes 列必须填写被影响的断言ID
- confidence：H=多源交叉验证，M=单源但来源可信，L=推测/二手转述

## 知识包增量写入（由知识管理员 consolidation 负责，调研员不直接写知识包）

> **新协议（zhishibao claims.jsonl）下，调研员不再直接写知识包 json**。单源分析产出的 key_claims（SPO 表格）+ evidence + characteristics 是知识管理员的提取源，由知识管理员在 consolidation run（每5批次）时用 zhishibao skill ingest 写入 claims.jsonl。
> 旧协议的 `knowledge-pack-{项目名}.json` 的 source_registry/claim_registry/graph.nodes 增量写入已废弃--新协议用 `claims.jsonl`（断言真相源）+ `index/knowledge.db`（影子索引）+ `views/L0` 视图，由 zhishibao skill 自动维护。

调研员单源分析（A*.md）产出后：
1. 确保 key_claims 是 SPO 表格格式（见 standards/extraction-format.md）
2. 在 `extracted_claims_confirmation` 段留空（知识管理员 consolidation 时回填 db_claim_id）
3. 不直接调 knowledge-ingest.py、不直接写 claims.jsonl--这由知识管理员在 consolidation run 统一做（含融合纪律：先查后写、关系判定、仲裁）

### SYNTHESIZE后的处理

跨源对比（对比-C*.md）完成后，对本轮所有 `single_source_pending` 的 claim/node 的处理（多源一致->cross_validated / 多源矛盾->contested / 被推翻->superseded）也由知识管理员 consolidation run 执行，调研员只产出对比-C*.md 文件。

## 跨源对比

如果本轮多个采集记录涉及同一概念或同类主题，写跨源对比分析到 `02-分析提取/跨源对比/对比-C{id}*.md`：

```
# 跨源对比：{对比主题}

对比ID: C{3位}
涉及采集记录: S{id}, S{id}, ...

## 对比维度
- 维度1：观点A（S{id}） vs 观点B（S{id}）
- 维度2：方法差异

## 共识
所有来源一致认可的结论

## 分歧
各来源不一致的地方，注明采集ID持哪方

## 综合判断
基于多源分析的归纳结论，用于知识包条目写入
```

## New Directions 提取

写分析的同时提取：
- 哪些结论可以确认？
- 哪些方向值得继续深挖？
- 哪些新关键词或子问题浮现？

这些 New Directions 必须在同一轮写入 `task_queue.md` 或 `run-state.md` 的 focus/explore 线索段（不写 project.config.md）。P0/P1 缺口必须立即生成 DISCOVER 任务，不得只记录为文本，也不得等用户确认。
